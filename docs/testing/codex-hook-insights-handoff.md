# Codex registry-hook insights: options A/B and implementation handoff

**Status:** investigation and design handoff, **not** an implemented feature or release approval. Snapshot: local branch `review/pr-1972` at `094e568e` (not pushed at this handoff). Recheck the branch, PR #1972, Codex version, documentation, and CI before acting. This document describes a proposed architecture, not an approved security design. Do not interpret installed hooks or generic hook events as verified execution.

## Outcome required

Attribute one actual Codex hook run and its outcome to **one uniquely verified Registry component/version and exact script**, in a particular session and effective scope. Keep installation, trust/enabled status, possible eligibility, actual execution, and script effectiveness distinct. A hook that did not leave complete trustworthy evidence is **unknown**, not a measured zero. Never upload hook stdin, stdout/stderr, command text, prompts, script contents, credentials or provider output as activity evidence. Preserve existing component-report coverage and owner authorization.

Option A is **managed app-server sessions only**; Option B is a **separate ordinary CLI evidence collector**. B can reuse A's pinning, evidence schema, delivery, matching, UI and privacy work, but does *not* inherit A's Codex-reported execution provenance. Neither option covers ordinary `codex`/`codex exec` by merely installing the app-server or patching Observal's telemetry hooks.

## Existing code and missing integration

- Registry: `packages/observal-shared/observal_shared/harness_registry.py` lists Codex hook capability, project/user `.codex/hooks.json`, `.codex/hooks` scripts and four mapped hook events. It intentionally has **no** `hook_evidence_extractor`. A capability entry is not verified attribution.
- Server agent generation: `observal-server/services/harness/codex.py` creates agent TOML and MCP config and passes through skill components, but **ignores `ctx.hook_configs`**: registry hooks are not actually written as part of the Codex agent pull. `observal-server/services/harness/helpers.py` has other harnesses' hook-file/config helpers; Codex needs native JSON matcher-group generation, script installation and binding metadata, not an invented TOML shape. Keep Observal's *telemetry* `UserPromptSubmit`/`Stop` hooks (`observal_cli/harness_specs/codex_hooks_spec.py`) distinct from registry hook components.
- CLI: `observal_cli/harness/codex.py` has no Codex `standalone_hook_binding`, `bind_pulled_hooks` or `verify_hook_binding`; the base adapter defaults to unverified. `observal_cli/cmd_pull.py` records hook command/event, config, script integrity for adapters that supply bindings. `observal_cli/layer.py` already snapshots Codex hook config hashes and maps verified hook bindings but needs precise Codex active-config and script checks (user/project/inline TOML/plugin/managed sources, trust/disabled, duplicates, shadow, bytes and version). Current layer display paths alone do not prove execution.
- Existing delivery: `observal_cli/hooks/session_push.py` reads Codex rollout JSONL through `observal_cli/sessions/base.py` and a durable outbox. `observal-server/services/component_activity/{evidence_projector,hook_projector,hook_matcher,hook_queries}.py` extracts canonical source records, matches a SHA-256 of `event + NUL + command` to a uniquely verified layer candidate, and publishes versioned coverage. `observal-server/services/session_parsers/hook_evidence.py` dispatches only Claude Code and Pi. A live app-server notification is **not** automatically a canonical source record. Do not splice unauthenticated notification text into Codex JSONL or use `extra_records` without designing source custody, checkpoint/replay, layer hash and source-completeness rules.
- The hook matcher currently considers a verified, standalone configured hook `eligible` unless session context says otherwise. For Codex, being configured does not guarantee trust/enabled/matcher eligibility or that the collector saw every notification. Design a **Codex-specific fail-closed eligibility/completeness contract** before enabling a measured no-run denominator. Version `HOOK_MATCHER_VERSION` (packed into `publication_version()` with other matchers) when semantics change; test forced replay and stale publications.

## Option A — managed app-server sessions (recommended first, **not yet built**)

**Boundary:** Observal is the client, or a transparent **stdio JSON-RPC proxy in front of an existing app-server client**, for a session it explicitly manages. The user/client must start sessions through that entry point; a separate standalone `codex` process cannot be observed retroactively. Choose and document the client entry point and how consent, approvals and interactive input continue to work before implementation. The app-server's WebSocket transport is documented as experimental/unsupported for production; prefer a reviewed local stdio design rather than assuming a remote WebSocket service is deployable. Test 0.165.0 specifically.

Proposed sequence, each link a gate rather than an assumption:

1. **Install/pin** registry command hooks into native `hooks.json` matcher groups and write scripts. Generate an unambiguous binding per component/version; verify active user/project source, precedence, Codex project trust, individual hook trust hash, enabled state, matcher, handler type, script bytes, and absence of a duplicate or shadow. Treat inline TOML, plugins and managed hooks as possible conflicting/effective sources; unreadable/unresolved sources fail closed. Never overwrite the user's other hooks. Verify `CODEX_HOME` and the actual working directory, not only canonical default paths.
2. **Start and observe** Codex through the managed connection. Forward all JSON-RPC traffic unchanged; preserve authentication, approvals, notifications, failures and shutdown. Confirm from an actual 0.165.0 controlled run that `hook/completed` is delivered to this connection for the chosen event, including silent success, exit 7, blocked, stopped, concurrent handlers and subagent scope. Determine exact handler-ID semantics across user/project sources, order, repeated turns and config reloads. Reject unknown IDs, event/status combinations, incomplete notifications or ambiguous IDs. Do not assume `sourcePath` alone identifies a handler.
3. **Bind the notification to effective config and bytes.** Take an authoritative, time-relevant snapshot of Codex's loaded hooks (e.g. `hooks/list`/effective config where supported) and compare to the pinned files. Establish that `id`, `sourcePath`, event, handler type, scope and order map to exactly one effective command, then to one verified registry pin. Address time-of-check/time-of-use script or config mutation: reading a hash before/after is not, by itself, proof of which bytes Codex executed in between. Investigate frozen immutable copies or a first-party stronger binding; if that proof is unavailable, label the observation honestly or leave it unsupported. A successful status is evidence of hook-run outcome, **not** of the hook achieving its intended purpose.
4. **Durable, private delivery.** Persist the minimal first-party-derived record with thread/turn/run identity, source/version, binding digest, status and event time in an Observal-controlled bounded outbox **before** acknowledging it as measured. Deduplicate, handle crashes, reconnects, missing event sequences and delayed source rollout. Couple it to the same scoped user/project/session and contemporaneous layer snapshot that the warehouse projector uses; authenticate ingestion and provide idempotent replay. An explicit lost collector window or unobserved thread is unsupported, never zero. Do not store `entries`, command, input/output or tokens. Define deletion/retention and a schema/migration only after choosing an ingestion contract. Reconciliation of rollout JSONL alone cannot recover lost live notifications.
5. **Project/report** only uniquely verified first-party completions. Report success-with-output versus silent success only if the app-server metadata can prove output presence without exporting it; classify blocked/failed/stopped conservatively after controls. Publish unsupported/version-unverified/missing-source/collector-gap states, collisions and unmatched candidates. Add Codex to the registry's hook extractor only after the end-to-end path and denominator rules pass; bump the matcher version and re-project affected sessions. Keep unmanaged sessions unsupported rather than measured no-hook runs.

**Outstanding product decision:** which client is intentionally managed? A new `observal ...` launch command, a transparent replacement of a specific client's `codex app-server` stdio command, or something else. CLI syntax changes require the corresponding `observal_cli/skills/` documentation. Remote VS Code/TUI sessions are **not** in scope until their transport and subscription behavior are independently proven. No assumption that an arbitrary `codex --remote` client broadcasts hook notifications to an unrelated observer.

## Option B — ordinary Codex CLI (`codex` / `codex exec`), independent follow-up

These runs do not expose the app-server's live notifications to Observal's managed connection and the saved rollout lacks an exact-hook/outcome record. **Option B reuses A's installation/pin verification, warehouse/report semantics, privacy gates and tests, but needs a different execution provenance.** Candidate approaches (not approved implementations):

1. **Upstream first-party source:** ask Codex to persist per-handler run identity, configured binding or execution-time digest, event, exit/block status, session/turn IDs and completeness in its rollout or another documented durable interface. Retest supported versions and project/user trust, then extract without trusting prompt/tool text. This gives the clearest independent evidence if available.
2. **Managed command runner:** install a reviewed Observal launcher *as the registry hook command* which validates a pin, preserves original stdin/stdout/stderr, timeout, exit/stop/block behavior and runs the exact script, then writes a minimal crash-safe outcome receipt. A runner's **self-receipt is not independent Codex attestation**: establish its threat model, session correlation, crash/missing-record behavior, same-user tampering resistance, and whether it warrants a separately labelled `Observal-managed runner observed` claim. Do **not** silently equate its receipts with A's Codex-reported runs or call a telemetry/session-push hook a registry-hook receipt. The existing roadmap explicitly calls for human review of this attestation design before a verified-execution claim.
3. **Other independently observed broker:** feasible only if it intercepts every supported hook invocation and records actual command/bytes/outcome without relying on the hook's assertion. Document process, trust, privacy and completeness guarantees, and prove them on 0.165.0 before an opt-in. Merely parsing terminal display, `codex exec --json` error items, file configuration, `Stop` or general task-completion markers is insufficient.

Option B could be narrower than all ordinary CLI executions: any handler type, event, platform, async/background mode, untrusted project or unobserved launch path outside its proven boundary stays unsupported. Running A's app-server collector in the background does not make B automatic.

## Verification matrix and release gates for either option

- **Native positives:** exact verified project and user installs; silent exit 0, output exit 0, exit 7, blocking where Codex actually supports it; multiple distinct matching handlers, repeated turns and versioned replay. Prove the source contains a per-handler identity and outcome, not only the UI saying a hook fired.
- **Native negatives:** no-trigger/no-hook, disabled feature, unreviewed/untrusted hook, untrusted project, edited config/script, hash-change trust reset, duplicate identical handlers, same-name shadow, user/project source collision, inline TOML/plugin/managed conflict, missing source, unsupported CLI version, malformed/tampered/duplicate receipt, collector crash/disconnect before completion, async completion after turn, script replacement during execution. Treat each uncertainty as unsupported or unattributed, **never a false zero**. Compare actual `hooks/list`/effective config and trust behavior; tests must not bypass trust except as an explicitly marked control.
- **Delivery/security:** disposable credential-free native provider and scripts; Registry-backed verified install; automatic delivery before reconcile and forced replay; source-to-layer hash joining; only authorized owner can see activity, unrelated and anonymous callers denied; no commands, arguments, prompts, script bodies, output or credentials in ClickHouse rows, APIs, CLI, HTML exports, insight model inputs or screenshots. Bound buffers/record sizes and test the restart path. Test container build and live report, not mocks alone.
- **Policy:** CI on the exact pushed head, full PR-diff code/privacy/security review, screenshots if UI changes, human authorship and approval under `AI_POLICY.md`. Do not push this document or claim release approval without the owner reviewing its content. Credential-like material seen previously must be confirmed inactive/rotated before credential-backed testing.
