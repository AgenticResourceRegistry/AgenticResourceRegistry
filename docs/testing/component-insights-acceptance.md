### First-upload reliability finding and fix

The initial real snapshot upload returned 200 and `stored=true`, but its mapping was not immediately visible; a second idempotent upload produced two complete verified mappings. `insert_layer_snapshot` previously sent its ClickHouse INSERT without `wait_for_async_insert=1`, then the API immediately queried the row for extraction. With asynchronous inserts, a snapshot INSERT acknowledgement alone need not guarantee that the immediately following extraction read sees the row. The local fix adds the same wait setting already used for session-event inserts. The first observation alone cannot distinguish an extraction read miss from buffered mapping/marker publication, so this is a targeted reliability hardening rather than a proven complete explanation for every delayed mapping. After an isolated API/worker rebuild (and LB restart to refresh its upstream), **new, empty-pin v2 test snapshots** were published on their first uploads and received complete zero-occurrence extractions without retries. One first-upload marker was visible on the first poll; the other took a later read to appear. An empty-pin extraction tests publication reliability, **not component presence**. `tests/test_layer_snapshot_v2.py` asserts the query option; do not count the pre-fix retry as a normal first-upload pass.
