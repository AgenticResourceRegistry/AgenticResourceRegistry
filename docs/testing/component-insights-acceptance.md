Local acceptance on #1779 head `2264248e` (17 October 2026), with the follow-up on commit `2d3d26d89`. **Automatic delivery was exercised for Claude Code only, not every harness.** The prior real Pi skill result in the PR handoff (two verified-present sessions, one confirmed load, 60 *project-wide* legacy-hash sessions excluded from presence) remains separate from this run.

## One owner-authorized historical case

The requester authorized a read of traces using their authenticated `admin@demo.example` account on `internal.observal.io`. I selected **one session belonging to that same account**: a Pi session from 30 May 2026, ID `019e791c…`. The detail API necessarily returned events to the authenticated client; I inspected only its response structure and event count, not the events' text, prompts, arguments, or credentials, and did not save the response. I did **not** inspect another user's session. The earlier third-party Agent investigation in the private handoff is not a second consented case.

| Stage | Observed for this case | Interpretation |
| --- | --- | --- |
| Account, harness and time | Current authenticated account's user ID matches the session owner; Pi, 30 May 2026 | In scope for this read; age alone does not prove a legacy hash. |
| Session metadata | 17 returned events; list reports six tool results and an Agent ID | An Agent ID/tool-result count says nothing about the installed component. No tool name or transcript content was used as installation proof. |
| Contemporaneous layer hash / installed component identity | The authenticated session list/detail API does not expose the session's layer hash, pin/version or snapshot identity | Hash schema **unknown** from this API; cannot identify a same-user/project/hash snapshot. This is **not** a finding that no snapshot exists in the warehouse. |
| Snapshot, extraction, source projection and usage | No independently joinable installation record was available through these authorized reads; no historical re-ingest or projector replay attempted | Installation and component-specific projection/use **unestablished**, not measured zero. No component Insights report or distinct-user attribution was created from this session. |

A separate read-only check of this machine's local Observal outbox found no row for this session ID; that does not prove anything about the internal server's ClickHouse snapshot table. To recover it as *verified* would require separately permitted, contemporaneous evidence binding the actual installed component UUID/version/alias to this user, project, harness and session time. Today's install, an Agent pin, memory, Bash, or an imported Agent report cannot supply that proof.

**Product decision for #1779:** verified-only presence/use stays unchanged. Explain historical evidence gaps and the no-cohort 422 without treating unknown as zero. Do not backfill or add owner-reported history to verified use rates, distinct-user counts, recommendations or review signals. A future owner-reported view would require its own lower-trust label, permissions, and denominator; it is not implemented here. The case above does not demonstrate that historical recovery is universally impossible; it demonstrates that this case **could not be independently verified with the available authorized evidence**.

### First-upload reliability finding and fix

The initial real snapshot upload returned 200 and `stored=true`, but its mapping was not immediately visible; a second idempotent upload produced two complete verified mappings. `insert_layer_snapshot` previously sent its ClickHouse INSERT without `wait_for_async_insert=1`, then the API immediately queried the row for extraction. With asynchronous inserts, a snapshot INSERT acknowledgement alone need not guarantee that the immediately following extraction read sees the row. The local fix adds the same wait setting already used for session-event inserts. The first observation alone cannot distinguish an extraction read miss from buffered mapping/marker publication, so this is a targeted reliability hardening rather than a proven complete explanation for every delayed mapping. After an isolated API/worker rebuild (and LB restart to refresh its upstream), **new, empty-pin v2 test snapshots** were published on their first uploads and received complete zero-occurrence extractions without retries. One first-upload marker was visible on the first poll; the other took a later read to appear. An empty-pin extraction tests publication reliability, **not component presence**. `tests/test_layer_snapshot_v2.py` asserts the query option; do not count the pre-fix retry as a normal first-upload pass.
